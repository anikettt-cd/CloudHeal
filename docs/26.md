1. Project Vision

CloudHeal is our own private-cloud management and intelligent self-healing platform.

Its purpose is to manage supported infrastructure through a common interface and provide higher-level incident detection, classification, evidence collection, deterministic remediation policies, safe execution, independent verification, persistent incident history, and measurable recovery performance.

The central architectural principle remains:

Kubernetes handles standard orchestration. CloudHeal provides the higher-level self-healing intelligence.

Kubernetes already manages scheduling, desired-state reconciliation, container lifecycle, ordinary restarts, and standard workload health reporting.

CloudHeal should focus on problems that require higher-level decisions, such as identifying meaningful incidents, interpreting evidence, determining whether remediation is justified, coordinating approved recovery, verifying the outcome, and recording the result.

The initial environment includes a MacBook Air and three Windows laptops connected through Tailscale. These machines are a development and demonstration environment, not the permanent definition of CloudHeal’s architecture.

Core workflow

Observe → Classify → Gather Evidence → Evaluate Policy → Remediate → Verify → Record

The project must demonstrate real infrastructure behavior, not merely a dashboard, chatbot, or collection of recommendations.

3.2 Kubernetes Adapter

The Kubernetes adapter obtains real deployment and pod status from K3s.

It exposes information including:

* Desired replicas.
* Ready replicas.
* Available replicas.
* Pod phase and readiness.
* Container state.
* Container restart counts.

The adapter is already being used by the incident detector and recovery verification workflow.

3.3 Incident Detector

The detector examines deployment status and identifies degradation based on three conditions:

* Ready replicas are below the desired replica count.
* Available replicas are below the desired replica count.
* One or more pods are unhealthy.

The third condition is important: a deployment may have the expected number of available replicas while still containing an unhealthy pod.

The detector can create or update a persistent incident classified as:

DEPLOYMENT_DEGRADED

When the deployment becomes healthy, the detector attempts to resolve an existing incident through the database layer.

3.4 Recovery Executor

The recovery executor:

1. Claims a recovery attempt.
2. Invokes the supported restart operation.
3. Polls deployment status.
4. Checks whether the workload has returned to a healthy state.
5. Records a success, failure, or uncertain outcome.

Verification considers the desired, ready, and available replica counts, pod readiness, and pod phase.

The executor uses bounded polling rather than treating an accepted restart request as proof of recovery.

3.5 Background Incident Monitor

The background monitor is configured through environment variables and periodically evaluates selected deployments.

The current configuration is:

export KUBECONFIG="$HOME/.kube/cloudheal-k3s.yaml"
export CLOUDHEAL_MONITOR_TARGETS="cloudheal-test/cloudheal-demo,cloudheal-test/cloudheal-recovery-demo"
export CLOUDHEAL_MONITOR_INTERVAL_SECONDS=10

The logs previously confirmed that the monitor was checking both configured targets every ten seconds.

Verified: The background monitor detects deployment degradation through the incident detection workflow.

Verified: When automatic recovery is enabled, the background monitor invokes the recovery executor with the automatic trigger. The executor claims a recovery attempt, requests a deployment rollout restart, independently verifies deployment health, and persists the outcome.

Live validation: Incident #7 was automatically recovered and marked RESOLVED. Recovery attempt #2 finished with SUCCEEDED after the test deployment returned to 3/3 ready and available replicas. The protected cloudheal-demo deployment remained healthy at 1/1.

Safety note: Automatic recovery is disabled by default and should only be enabled for explicitly configured, appropriate targets.

3.6 Database and Incident History

The existing database layer records incidents, recovery attempts, and associated events.

The history endpoint is:

GET /incidents/history?limit=10

Incident history contains the original incident evidence, timestamps, status, and associated recovery attempts where applicable.

Persistent history has been verified through live API responses. Broader database durability and consistency testing across service restarts remains a separate potential task.

8. Safe Automatic-Recovery Test Plan

The core automatic-recovery cycle has already been demonstrated on cloudheal-recovery-demo. Keep this plan as a checklist for future failure-mode tests; do not repeat the same fault injection unnecessarily.

The test must:

1. Introduce a reversible failure in the dedicated test deployment.
2. Let the configured monitor detect the incident.
3. Observe whether the automatic recovery policy is invoked.
4. Confirm that the action is authorized.
5. Observe the recovery attempt and its status.
6. Verify the deployment using real Kubernetes state.
7. Confirm the incident is resolved.
8. Confirm the complete attempt and incident history.
9. Restore the deployment to a healthy state even if the recovery fails.

The experiment must distinguish between:

* A monitor that detects and records incidents.
* A monitor that requests recovery through policy-controlled orchestration.
* A recovery action that is merely accepted.
* A recovery action that completes.
* A recovery action that is independently verified as successful.

Do not use uncontrolled resource exhaustion. Do not repeatedly restart the deployment merely to generate events. Use bounded retries and preserve the original test application.

If a future environment does not support automatic recovery, document the observed behavior and make the smallest justified change before repeating the relevant test.

11. Longer-Term Architecture

Once the Mac workflow is complete, continue with the agreed architecture.

Self-healing core

Maintain infrastructure-independent models for observations, incidents, evidence, decisions, remediation attempts, verification results, audit records, and metrics.

Infrastructure adapters

Use Kubernetes APIs for Kubernetes-managed workloads. Future adapters may support other infrastructure providers after the Kubernetes adapter and core contract stabilize.

Deterministic policy

Before executing an action, evaluate:

* Target validity.
* Supported action.
* Permissions.
* Incident classification.
* Attempt limits.
* Cooldown.
* Concurrent actions.
* Verification capability.
* Escalation requirements.

The exact policy implementation must be inspected before changes are made.

Safety

* AI recommendations never authorize their own execution.
* Use least-privilege Kubernetes permissions.
* No unrestricted AI shell access or unrestricted Docker-socket access.
* A timeout is not proof of failure.
* An accepted action is not proof of success.
* Node unavailability is not proof that the workload terminated.
* Avoid duplicate recovery actions and uncontrolled retry loops.
* Maintain a bounded and auditable recovery process.

AI and multi-provider support

Defer AI-assisted diagnosis, constrained planning, and additional provider adapters until the deterministic Kubernetes workflow is reliable.

12. Evaluation Roadmap

After the complete recovery workflow is demonstrated, establish repeatable experiments and record:

* Incident detection time.
* Recovery duration.
* Application downtime.
* Recovery success rate.
* False-positive rate.
* Unnecessary remediation.
* Rejected unsafe actions.

Compare Kubernetes-native behavior with CloudHeal observation-only and CloudHeal-controlled remediation where appropriate.

Keep unsuccessful trials in the results. Record actual timestamps and outcomes rather than inferring recovery performance from API responses alone.

13. Windows Integration — Deferred

Windows worker integration is not the immediate task.

The older Windows-hosted WSL2 K3s pilot had a reachable API through a Windows portproxy, but that setup did not establish working multi-node K3s networking.

The historical networking concerns included:

* WSL NAT and changing WSL IP addresses.
* A TCP API forward that did not prove node-to-node connectivity.
* Kubelet communication.
* Flannel/VXLAN pod networking.
* High and variable Tailscale DERP relay latency.

Those details should be revalidated when Windows integration resumes.

Do not attempt to join the Mac VM to the older Windows K3s cluster based only on API reachability. The current Mac K3s pilot is a separate environment and is already working for the Mac validation phase.
